## Summary of `unknown` / `reference-gap` / `likely-quantum-vulnerable-unconfirmed` assets

None of this run's components received `unknown`, `reference-gap`, or `likely-quantum-vulnerable-unconfirmed` labels — every cryptographic operation in the current codebase is clearly evidenced:

- `crypto:algorithm:ml-kem-768`, its public/private keys → `quantum-resistant-at-appropriate-strength` (final NIST standard, exact parameter set confirmed).
- `crypto:algorithm:aes-256-gcm`, `crypto:algorithm:sha-256` → `quantum-resistant-at-appropriate-strength`.
- `crypto:algorithm:hkdf-sha256` → `parameter-and-purpose-dependent` (KDF construction needing human cryptography review of its context-binding and salt choice — this is the same open item the prior run's `design-01` approval already flagged as needing "qualified cryptography review before production use").
- All material assets (shared secret, ciphertexts, derived key, IV) → `not-classified` (not algorithms).

**No `quantum-vulnerable` assets remain in this run's CBOM.** The prior run's three `quantum-vulnerable` components (RSA-OAEP algorithm, RSA-OAEP public key, RSA-OAEP private key) have no counterpart in this pass — current source evidence shows no RSA/OAEP code path anywhere in `app.js` or `app.bundle.js`. [brief.md](../../brief.md) still describes RSA-OAEP, but this is flagged in [findings-report.md](findings-report.md) as stale documentation, not treated as a second code path or given a classification row.

Limitation worth tracking: `crypto:algorithm:hkdf-sha256`'s `parameter-and-purpose-dependent` label is not a finding that anything is broken — it reflects that the bundled algorithm reference does not specifically enumerate HKDF, and that the exact context-binding/salt construction here has not been independently reviewed by a cryptographer, consistent with the caveat already recorded when this design was approved for implementation.
